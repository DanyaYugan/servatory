# Версионирование Servatory

Формат: **MAJOR.MINOR.PATCH** — три числа, без ведущих нулей.
Дополнительно: суффикс стадии и, при необходимости, метаданные сборки.

```
1.4.2              стабильная версия
2.0.0-alpha.3      альфа, третья сборка
1.0.0-beta.2       бета, вторая сборка
1.0.0-rc.1         кандидат в релиз
1.4.2+build.17     метаданные сборки (не влияет на сравнение)
```

## Что означает каждая цифра

| Часть | Когда увеличивается | Примеры |
|---|---|---|
| **MAJOR** | несовместимые изменения: новый дизайн, смена API, формата конфига, схемы БД без обратной совместимости, удаление функций | 1.x.x → 2.0.0 |
| **MINOR** | новые возможности без поломки старого: бот, роли, бэкапы, новые страницы | 1.4.0 → 1.5.0 |
| **PATCH** | исправления, оптимизация, мелкие правки без новых функций | 1.4.2 → 1.4.3 |

Правила:

```
при увеличении MAJOR  MINOR и PATCH обнуляются: 1.9.3 → 2.0.0
при увеличении MINOR  PATCH обнуляется:         1.9.3 → 1.10.0
при увеличении PATCH  меняется только третья:   1.9.3 → 1.9.4
```

## Стадии

| Стадия | Кто тестирует | Что разрешено | Гарантии |
|---|---|---|---|
| **alpha** | разработчики | любые изменения, функции могут исчезнуть | нет; миграции не обещаются |
| **beta** | внешние пользователи | фиксы, мелкие правки; функции заморожены | миграция с прошлой беты |
| **rc** | желающие | только критичные фиксы | миграция с прошлой rc и с betas |
| **stable** | все | по правилам SemVer | миграции и обратная совместимость в рамках MAJOR |

Что можно и нельзя:

```
alpha   можно менять схему БД без миграции, ломать API, переименовывать поля
beta    API и схема стабильны; новые поля только добавляются
rc      меняются только баги и тексты; никаких новых функций
stable  только патчи и минорные добавления, удаление — в следующем MAJOR
```

## Путь до 1.0.0

```
0.1.0-alpha.1   первый каркас: /health, база, вход
0.2.0-alpha.1   провайдеры и список контейнеров
0.4.0-beta.1    установка, удаление, обновление
0.6.0-beta.1    бэкапы, группы, веб целиком
0.9.0-rc.1      заморозка функций, только фиксы
1.0.0           стабильный релиз
```

До 1.0.0 действует правило: `0.MINOR.PATCH`, где MINOR — значимая веха,
PATCH — исправления внутри вехи. Ломающие изменения допустимы, но каждая
alpha/beta должна иметь заметки о миграции, если данные уже используются.

## Где версия фиксируется

```
git tag           v1.2.3 (аннотированный тег)
код               app/version.py: __version__ = "1.2.3"
API               GET /api/v1/meta → {"version": "1.2.3", "schema": 7}
Docker            ghcr.io/servatory/servatory:1.2.3, :1.2, :latest
схема БД          отдельно: schema_version, не совпадает с версией продукта
changelog         CHANGELOG.md, разделы по версиям
```

Важно: версия продукта и версия схемы БД — разные числа. Схема может
увеличиваться на патчах, если понадобилась миграция.

## Теги образов

```
1.2.3   точная версия, для продакшена
1.2     последняя в линии 1.2, обновляется патчами
1       последняя в мажоре, может прыгнуть на 1.3
latest  последняя стабильная, не для продакшена
```

`alpha`, `beta`, `rc` публикуются только с точным тегом и суффиксом:

```
1.3.0-beta.1, 1.3.0-rc.1
```

## Совместимость

```
API            /api/v1 живёт весь MAJOR; удаление — только в 2.0.0
схема БД       миграции только вперёд; откат — из копии перед обновлением
конфиг         новые поля с значениями по умолчанию; старые не удаляются в MINOR
устаревание    в MINOR помечаем «устарело», удаляем в следующем MAJOR
```

## Процесс релиза

```
1 заморозка: с этого момента только фиксы
2 CHANGELOG: Added / Changed / Fixed / Removed / Security
3 тесты: юнит, интеграционные, ручной сценарий из приёмки
4 версия: __version__, тег vX.Y.Z
5 образы: сборка amd64/arm64, теги X.Y.Z и X.Y
6 заметки: что нового, что ломается, как мигрировать
7 проверка: установка с нуля и обновление с прошлой версии
```

## Частота

```
PATCH   по мере необходимости, без ожидания
MINOR   когда накопились функции; ориентир — раз в 1–2 месяца
MAJOR   когда без поломки не обойтись; заранее объявляем
```

## Что считается ломающим изменением

```
удаление или переименование поля API
изменение смысла существующего поля
удаление страницы или кнопки, которой пользуются
формат конфига, требующий ручной правки
схема БД без автоматической миграции
новый дизайн интерфейса (по договорённости — MAJOR)
```

Не считается ломающим:

```
добавление поля, страницы, кнопки
новый необязательный параметр
изменение текстов и оформления без смены сценариев
оптимизация без изменения поведения
```

## Примеры

```
1.0.0        первый стабильный
1.0.1        исправлен откат при обновлении
1.1.0        добавлены группы и порядок
1.1.1        исправлена сортировка в группе
1.2.0        добавлены бэкапы
2.0.0        новый дизайн и API v2, старый API удалён
```
