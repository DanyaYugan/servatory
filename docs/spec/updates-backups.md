# Обновления и бэкапы

## Обновления

### Поиск

```
источник       digest образа в реестре против локального
версия         метка OCI → команда из hub.update.cmd → дата сборки
сравнение      если версия изменилась — «обновление»;
               если digest изменился, а версия та же — «пересборка»
кеш            /data/cache/versions.json, сбрасывается при смене digest
```

### Политика

```
manual    только показывает
notify    показывает и уведомляет (по умолчанию)
auto      обновляет в разрешённое окно
```

Окно по умолчанию: `sun 04:00-05:00`, настраивается на сервис.

### Конвейер обновления

```
1 проверить права (service.action.update) и блокировку
2 записать состояние до: image id, digest, конфиг, маршруты
3 бэкап по политике (если включён)
4 pull нового образа
5 пересоздать контейнер (compose up -d <service>)
6 ждать running и healthy (таймаут 90 с)
7 проверить health-url и маршрут (если есть домен)
8 при ошибке: вернуть тег на прежний image id, пересоздать, проверить
9 записать в audit и operations, уведомить
```

Откат невозможен, если:

```
образ удалён из локального кеша
том изменён несовместимо (записываем предупреждение, но не блокируем)
```

В этих случаях статус `rolled_back: false` и сообщение «нужен ручной разбор».

### Массовое обновление

```
POST /api/v1/updates/apply {"services": [...], "confirm": true}
последовательно, по одному сервису
при ошибке одного — продолжать остальные, собрать отчёт
итог: {"ok": ["a","b"], "failed": [{"id":"c","error":"..."}]}
```

## Бэкапы

### Что копируем

```
том Docker      через вспомогательный контейнер с --volumes-from
каталог /data/services/<name>   обычным tar
база Postgres   pg_dump в контейнере сервиса
конфиг хаба     hub.db + config.yaml (ежедневно)
```

### Куда

```
/data/backups/services/<service>/<timestamp>.tar.gz
/data/backups/services/<service>/<timestamp>.sql.gz
/data/backups/hub/hub-<timestamp>.db
```

### Политика

```
по умолчанию  хранить 7 дней и 5 последних копий на сервис
настраивается  hub.backup.keep, в UI — «сколько хранить»
удаление       только по политике, вручную — отдельной кнопкой с подтверждением
```

### Восстановление

```
1 выбрать бэкап, проверить место на диске
2 остановить сервис
3 распаковать том/каталог или залить дамп
4 запустить, проверить health
5 при ошибке — вернуть предыдущее состояние (сохраняем копию «до восстановления»)
```

### Проверка целостности

```
tar -tzf архив      перед записью в базу как ok
pg_dump             код возврата 0
размер > 0          иначе статус failed
```

### Ретеншн хаба

```
ежедневно: hub.db → /data/backups/hub/
хранить 14 копий, старые удалять
перед миграцией схемы: pre-migrate-<version>.db
```
