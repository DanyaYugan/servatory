# Решения и почему именно так

Семь вопросов, которые определяют продукт. Для каждого — варианты, плюсы,
минусы и выбранный вариант.

---

## 1. Аутентификация

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Только локальные учётки | просто, офлайн, нет внешних зависимостей | ещё один пароль, нет SSO |
| B. Локальные + OIDC | SSO, централизованный MFA | redirect URI, маппинг групп, зависимость |
| C. Локальные + LDAP | привычно в офисах | для дома избыточно |

**Выбрано: A в 1.0, архитектура под B.**

Причина: продукт должен работать сразу после установки, без второго сервиса
аутентификации. Провайдер входа закладывается с первого дня
(`auth.provider = local|oidc`), добавление OIDC не потребует переделки сессий.

---

## 2. Фронтенд

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Vue 3 + Vite | зрелая экосистема, готовые админ-компоненты | бандл ~120 КБ gzip, шаг сборки |
| B. Svelte | меньше кода и бандла | меньше готовых библиотек |
| C. JS без сборки | ноль зависимостей | админка превращается в кашу |

**Выбрано: A.**

Причина: интерфейс — админка (таблицы, формы, права, модалки). Выигрывает не
размер бандла, а готовые компоненты. 120 КБ для локальной панели не проблема.

---

## 3. Тома и каталоги

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Только контейнеры | минимум риска | установка «в один клик» не работает |
| B. Хаб создаёт тома и каталоги | удобно, бэкап знает данные | риск удалить лишнее, права |
| C. Гибрид | удобство + свобода | чуть больше кода |

**Выбрано: C с жёсткими рамками.**

```
по умолчанию      именованный том hub-<service>-data
хост-каталоги     только /data/services/<service>
произвольные пути расширенный режим compose
```

Бэкап томов — вспомогательным контейнером с `--volumes-from`.

---

## 4. Удалённые хосты

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Docker API по TLS | ничего не пишем, работает сразу | Docker API = root, сертификаты, нет NAT |
| B. Свой агент | безопаснее, работает за NAT, позже systemd | второй артефакт и его релизы |
| C. Агент Portainer | уже есть | зависимость от чужого API |

**Выбрано: A в 1.0, B в 1.1.**

Провайдер `docker-remote` сразу делается с подменяемым транспортом:
сейчас TLS, потом WebSocket-агент без переделки остального кода.

## 5. Лицензия

| Вариант | Плюсы | Минусы |
|---|---|---|
| MIT | максимально простой | нет патентной защиты |
| Apache 2.0 | патентная защита, дружелюбен к компаниям | длиннее, нужен NOTICE |
| AGPL | закрывает хостинг как сервис | отпугивает аудиторию |

**Выбрано: Apache 2.0.**

---

## 6. Языки

| Вариант | Плюсы | Минусы |
|---|---|---|
| Только русский | быстрее | продукт «для себя» |
| ru + en | шире аудитория, i18n сразу | поддержка двух текстов |
| Только английский | стандарт open-source | неудобно русскоязычным |

**Выбрано: ru + en, en по умолчанию.**

Добавлять i18n позже дорого: придётся переписывать шаблоны.

## 7. Секреты сервисов

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Хранилище в БД | установка в клик, экспорт, аудит | секреты в базе, нужен ключ |
| B. Только ссылки на `.env` | просто, привычно | UI не может создать, перенос вручную |
| C. Гибрид | удобно и безопасно | чуть больше кода |

**Выбрано: C.**

```
по умолчанию  секрет в хранилище, в базе шифрованным
              compose использует ${secret:name}
опция         внешний .env, значение не хранится
ключ          /data/key, 600, генерируется при установке
экспорт       только по выбору, зашифрованным архивом
```

Риск осознан: база и ключ лежат рядом, защита — права файлов и бэкап.
Для параноиков есть режим «только внешние файлы».
